# Day 8 — 2,400 req/s 기준 재측정

**목표** — 반복 누락이 본 부하 시작 후 첫 10초에 집중되는지 확인한다.

## 실행

[기존 준비·예열·저장 건수 대조 절차](2026-11-04-k6-baseline.md#재실행-절차-및-판정-기준)를 따른다. 이번에는 **2,400 req/s·4분·100 VU**로 1회 실행한다. Prometheus 수집과 Grafana 조회는 2초, API 요청률·응답 시간 집계는 8초로 맞춘다.

```bash
result_dir="load-test/results/$(TZ=Asia/Seoul date +%Y%m%d-%H%M%S)-2400-retest"
python3 load-test/measure.py --output "$result_dir" --rate 2400 --duration 4m
python3 load-test/aggregate_k6.py "$result_dir/k6-metrics.json.gz" \
  --output "$result_dir/k6-per-second.csv"
```

## 결과

2026-11-06 21:37:15~21:41:15 KST에 실행했다. 실제 요청률은 2,398.4 req/s였고, 575,636건 모두 성공했다. 중단된 반복은 0건, 시작되지 못한 반복은 365건(약 0.063%)이었다. 초별 요청·누락 합계는 k6 요약과 일치했다. [실행 결과](../../load-test/results/20261106-213715-2400-retest/)

| 누락 시각 (KST) | 기록 시작 후 | 누락 | k6 HTTP 대기 p95 / 최대 |
| --- | ---: | ---: | ---: |
| 21:38:31 | 76초 | 274 | 38.3 / 190.3 ms |
| 21:40:07 | 172초 | 81 | 53.5 / 129.4 ms |
| 21:40:32 | 197초 | 10 | 22.2 / 62.5 ms |

첫 10초에는 누락이 관측되지 않았다. 전체 누락의 약 75%가 21:38:31 구간에 발생했고, 같은 초에 100 VU 한도 경고가 기록됐다. 경과 시간은 수집 스크립트 시작 기준이다.

[조회 범위 21:35:50~21:41:50 KST](http://localhost:3000/d/ad4t9kv/renegade-backend-overview?from=2026-11-06T12:35:50.000Z&to=2026-11-06T12:41:50.000Z&timezone=browser). 아래 수치는 화면에서 읽은 근사치다.

- 서버 요청률은 본 부하 동안 약 2,400 req/s였고, 표시된 5xx는 0%였다.
- 21:38:31에 274건이 누락됐다. 서버 p95/p99는 직전 조회점인 21:38:30에 3.26/7.95 ms, 다음 조회점인 21:38:32에 3.05/6.98 ms였다. p99 약 32 ms는 21:38:34~38 조회점에서 보였다. 21:40:07에 81건이 누락됐다. 서버 p95/p99는 21:40:06에 3.27/6.05 ms, 21:40:08에 3.16/5.39 ms였다. p99 약 44 ms는 21:40:10~14 조회점에서 보였다. 서버 p99는 직전 8초 집계이므로 k6 초별 지표와 시각을 정확히 일치시키기 어렵다.
- 커넥션 풀은 21:38:30에 사용 중 4개·유휴 6개였다. 사용 중 10개·유휴 0개는 약 21:38:45 조회점에서 보였다. 두 번째 누락 구간의 풀 패널은 21:40:00과 21:40:15 조회점에서 모두 사용 중 5개·유휴 5개로 표시됐다. 표시된 대기 스레드는 0이었고, 평균 획득 시간은 약 0.06~0.25 ms 범위였다.
