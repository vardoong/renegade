# Day 8 — 2,400 req/s·150 VU 비교 실험

**질문** — 고정 VU를 100에서 150으로 늘리면 반복 누락이 줄어드는가?

## 실행

[100 VU 기준 재측정](2026-11-06-k6-2400-retest.md)과 동일한 2,400 req/s·4분, 재시작·예열·대기 및 수집 조건을 적용한다. `telemetry.js`의 `preAllocatedVUs`를 150으로 설정하고 시작 출력에서 최대 150 VU를 확인한다. 실제 실행 시각(KST)과 기준 조건에서 달라진 사항을 기록한다.

```bash
result_dir="load-test/results/$(TZ=Asia/Seoul date +%Y%m%d-%H%M%S)-2400-vu150"
python3 load-test/measure.py --output "$result_dir" --rate 2400 --duration 4m
python3 load-test/aggregate_k6.py "$result_dir/k6-metrics.json.gz" \
  --output "$result_dir/k6-per-second.csv"
```

## 판단

- 150 VU 실행에서 누락은 365건에서 1건으로 줄었다(99.7% 감소). 
- 이번 비교는 VU 여유가 부하 전달에 도움이 된다는 가설을 지지한다. 
- 150 VU 한도 경고와 서버 p99 피크는 여전히 관측됐다. 
- 조건당 1회이며, 시작 DB 행 수가 달라 효과의 재현성과 지연 원인은 판단 보류다.

#### Grafana

- Grafana 화면에서는 누락 시각 부근에 서버 p99가 약 52 ms까지 올랐고, 표시된 5xx와 풀 대기 스레드는 0이었다. 
- p99는 직전 8초 집계이며 화면 근사치다. 
- [Grafana 조회 범위 23:55~00:00 KST](http://localhost:3000/d/ad4t9kv/renegade-backend-overview?from=2026-11-06T14:55:00.000Z&to=2026-11-06T15:00:00.000Z&timezone=browser)

## Day 8 마무리

- 초반 집중 가설은 100 VU 재측정에서 지지되지 않았다. 누락 365건은 모두 첫 10초 이후에 발생했다.
- 150 VU 비교는 VU 여유가 부하 전달에 도움이 된다는 가설을 지지한다. 서버 처리 지연과 k6 측 지연의 기여도는 판단 보류다.
- Day 9에는 23:57:19 KST 전후의 k6 대기·연결·반복 시간과 서버 응답 시간을 먼저 대조한다. 추가 실행 여부는 이 자료를 보고 결정한다.
