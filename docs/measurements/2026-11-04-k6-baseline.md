## 재실행 절차 및 판정 기준

- 아래 명령은 저장소 루트의 zsh에서 실행한다. 
- 실제 재측정은 서버·DB·k6 CPU 관측 준비와 DB 건수 조회 방법을 갖춘 뒤 진행한다. 
- 각 반복 실행에서 동일한 환경·예열·VU 조건을 유지한다.

### 1. 실행 준비

1. 측정할 코드의 커밋 ID와 미커밋 변경을 기록한다.
   ```bash
   git rev-parse HEAD
   git status --short
   ```
2. PostgreSQL·Prometheus·Grafana가 실행 중인지 확인하고 Simulator와 다른 API 호출 작업을 중지한다.
3. 차량 ID 11~60이 모두 등록되어 있는지 확인한다.
4. IntelliJ에서 위에 기록한 설정으로 Backend를 재시작한다. Prometheus Targets의 `renegade`가 `UP`이고 지표가 수집되는지 확인한다.
5. 예열 전 telemetry 행 수를 기록한다. 예열 시작부터 종료 후 건수 대조까지 DB 초기화·데이터 삭제·Backend 재시작을 하지 않는다.
6. CPU 관측 수집을 시작한다. 반복 실행마다 별도 결과 폴더를 만든다.
   ```bash
   RUN_DIR="load-test/results/$(TZ=Asia/Seoul date +%Y%m%d-%H%M%S)-1200"
   mkdir -p load-test/results
   ```

### 2. 예열

각 명령이 정상 종료된 뒤 다음 명령을 실행한다. 예열 중 HTTP 오류나 체크 실패가 발생하면 원인을 확인한 뒤 다시 준비한다.

```bash
RATE=1 DURATION=5s k6 run load-test/telemetry.js
RATE=50 DURATION=1m k6 run load-test/telemetry.js
RATE=50 DURATION=1m k6 run load-test/telemetry.js
```

마지막 예열 종료 후 30초를 대기한다. 이 구간에 본 측정 직전 telemetry 행 수와 `telemetry_save_total`의 success·failure 누적값을 기록한다. Prometheus 값은 마지막 예열 요청 이후 수집된 값인지 확인한다. 준비가 지연되면 실제 대기 시간을 기록한다.

### 3. 본 측정 및 결과 저장

위에서 정한 `RUN_DIR`를 같은 터미널에서 사용한다. 결과 폴더 자체는 수집 스크립트가 생성하므로 미리 만들지 않는다. 이미 존재하는 폴더를 지정하면 덮어쓰지 않고 종료한다. Python 3.9 이상, 호스트의 k6·Docker CLI·macOS ps가 필요하다.

```bash
python3 load-test/measure.py --output "$RUN_DIR" --rate 1200 --duration 4m
```

- 시각 파일은 명령의 시작·종료를 나타낸다. k6의 초기화·종료 처리 시간도 포함하므로 실제 부하 구간은 콘솔 출력과 함께 확인한다.
- 시작 출력의 대상 주소·최대 VU, VU 한도 경고, 반복 누락과 중단 여부를 확인한다.

수집 스크립트는 k6를 직접 실행하고 그 PID의 CPU·RSS와 PostgreSQL 컨테이너의 CPU·메모리를 기본 5초 간격으로 기록한다. k6 콘솔은 화면과 파일에 함께 출력한다. 종료 시 수집을 중지하며 `Ctrl+C`로 중단해도 실행 종료 정보를 남긴다.

| 파일 | 내용 |
|---|---|
| `summary.json`, `console.log` | k6 요약과 콘솔 출력 |
| `db-resources.csv` | KST 조회 시작 시각, Docker CPU %, 메모리 사용량·비율, 수집 오류 |
| `k6-resources.csv` | KST 조회 시작 시각, k6 PID, macOS ps CPU %, RSS(KiB), 수집 오류 |
| `metadata.json` | 명령·부하 조건·단위·PID·시작/종료·수집 오류 |
| `start-time.txt`, `end-time.txt`, `exit-code.txt` | 실행 시작·종료 시각과 k6 종료 코드 |

Docker 조회 시간만큼 실제 표본 시점·간격에는 오차가 있다. macOS `ps`의 CPU 값은 프로세스 CPU 평균이며 정확한 최근 5초 사용률이 아니다. Docker와 ps CPU 값은 여러 코어 사용 시 100%를 넘을 수 있고 JVM의 `process_cpu_usage`와 분모·집계 방식이 다르므로 백분율을 직접 비교하지 않는다. 시각에 따른 변화와 응답 지연의 관계를 확인하는 보조 자료로 사용한다. 수집 자체의 부하도 있으므로 반복 실행에서 동일한 방식을 사용한다.

CSV의 `error`가 비어 있지 않으면 해당 표본은 유효한 측정값으로 사용하지 않는다. 수집 실패 시 스크립트는 0이 아닌 값으로 종료하며, `exit-code.txt`는 수집 상태와 별개로 k6 자체의 종료 코드를 보존한다. 서버 CPU는 기존 Prometheus/Grafana에서 같은 시간 범위로 확인한다.

수집 동작만 짧게 확인할 때는 아래 명령을 사용한다. 실제 요청이 전송되어 DB에 저장되므로 본 측정과 분리하고, 생성된 데이터도 초기 행 수에 반영한다.

```bash
python3 load-test/measure.py \
  --output "load-test/results/$(TZ=Asia/Seoul date +%Y%m%d-%H%M%S)-check" \
  --rate 1 --duration 15s
```

### 4. 종료 후 건수 대조

1. 다른 쓰기 작업을 중지한 상태에서 실행 중인 요청이 완료됐는지 확인한다.
2. 종료 후 telemetry 행 수와 저장 성공·실패 카운터를 기록한다. Prometheus는 종료 이후 수집값을 사용한다(수집 주기 15초).
3. 본 측정 직전 값과의 차이를 구해 k6 성공 체크 건수와 비교한다.

```text
DB 행 증가량 = 종료 후 telemetry 행 수 - 본 측정 직전 telemetry 행 수
저장 성공 증가량 = 종료 후 success 누적값 - 본 측정 직전 success 누적값
저장 실패 증가량 = 종료 후 failure 누적값 - 본 측정 직전 failure 누적값
```

### 5. 판정 기준

| 확인 항목 | 기준 |
|---|---|
| 실행 완료 | 종료 코드 0, 예정 시간 완주, 중단된 반복 0건 |
| 목표 부하 전달 | 실제 요청률 약 1,200 req/s, `dropped_iterations=0`. VU 한도 경고 유무도 기록 |
| HTTP·API 성공 | `http_req_failed=0`, `telemetry accepted` 체크 실패 0건 |
| 저장 건수 일치 | k6 성공 체크 건수 = 저장 성공 카운터 증가량 = DB 행 증가량 |
| 저장 실패 | 저장 실패 카운터 증가량 0건 |
| 응답 시간 | 평균·p95·p99·최댓값 저장. 현 단계에서 새로운 응답 시간 합격선은 설정하지 않음 |
| 관측 자료 | 동일 실행 구간의 서버·DB·k6 CPU, 기존 Grafana 지표와 조회 구간 저장 |

현재 스크립트는 반복당 요청 1회·체크 1회다. 모든 체크가 성공한 경우에만 총 요청 수를 성공 건수로 취급한다. 요청 수는 실행 경계 시각의 영향을 받으므로 정확히 288,000건으로 정하지 않고 실제 k6 출력을 기준으로 대조한다.

현재 스크립트에 thresholds가 없으므로 종료 코드 0만으로 위 기준을 충족했다고 판단하지 않는다. 각 지표와 저장 건수를 따로 확인한다. `dropped_iterations`가 출력에 없으면 콘솔 경고·완료 상태도 확인하고, 판단할 수 없으면 미확인으로 남긴다.

불일치나 반복 누락이 있으면 관측 결과로 기록한다. 목표 부하를 전달하지 못한 실행은 같은 부하 조건의 성능 비교에 사용하지 않는다. 관측 자료 누락이나 카운터 초기화가 있다면 해당 항목은 판단 보류로 남긴다. 새로운 실행 결과와 분석은 별도 실험 문서에 기록하고 이 절을 참조한다.

## DB 저장 건수 조회 및 대조 방법

IntelliJ의 해당 PostgreSQL DB 콘솔에서 아래 SQL을 실행한다. 조회는 자동 커밋 모드에서 수행한다. 수동 트랜잭션을 사용한다면 이전 조회 트랜잭션을 종료한 뒤 다시 조회해 최신 커밋 결과를 확인한다. 아래 쿼리는 데이터를 변경하지 않는다.

### 1. 대상 차량 등록 확인

```sql
SELECT COUNT(*) AS registered_vehicle_count
FROM vehicle
WHERE id BETWEEN 11 AND 60;
```

결과가 50이면 대상 차량이 모두 등록되어 있다. 부족하다면 다음 쿼리로 누락 ID를 확인하고 측정 전에 등록한다.

```sql
SELECT expected.id AS missing_vehicle_id
FROM generate_series(11, 60) AS expected(id)
LEFT JOIN vehicle AS v ON v.id = expected.id
WHERE v.id IS NULL
ORDER BY expected.id;
```

### 2. 측정 시점별 저장 건수 조회

아래 쿼리를 예열 전, 본 측정 직전, 본 측정 종료 후에 각각 실행하고 결과를 저장한다. 본 측정 직전 조회는 예열 종료 후 30초 대기 구간에 수행한다. 조회가 오래 걸려 대기 시간이 늘어나면 실제 대기 시간을 기록한다. 종료 후 조회는 k6가 종료되고 처리 중인 요청이 완료된 뒤 수행한다.

```sql
SELECT
    clock_timestamp() AS observed_at,
    COUNT(*) AS total_rows,
    COUNT(*) FILTER (WHERE vehicle_id BETWEEN 11 AND 60) AS target_vehicle_rows
FROM telemetry;
```

- `total_rows`: telemetry 전체 행 수. 초기 데이터 규모와 전체 저장 증가량 확인용.
- `target_vehicle_rows`: k6가 사용하는 차량 ID 11~60의 행 수. 대상 차량의 저장 증가량 확인용.
- 예열 전 값은 초기 환경 기록용이며, 본 측정의 저장 증가량은 반드시 **본 측정 직전 값**을 빼서 계산한다.
- 조회는 부하 실행 전후에만 수행한다. CPU 관측 비교 구간에 건수 조회 부하가 섞이지 않도록 본 측정 도중 반복 조회하지 않는다.
- `MAX(id)`나 시퀀스 값은 롤백 등으로 빈 번호가 생길 수 있어 저장 건수로 사용하지 않는다.
- Simulator와 다른 쓰기·삭제 작업은 전체 대조가 끝날 때까지 중지한다. 대상 차량 행 수만 조회해도 같은 차량에 대한 다른 쓰기가 섞이면 k6 단독 검증이 되지 않는다.

### 3. 저장 카운터 기록

본 측정 직전과 종료 후에 `/actuator/prometheus`의 `telemetry_save_total`에서 `result="success"`, `result="failure"` 값을 각각 기록한다. Prometheus/Grafana를 사용한다면 각 시점 이후 수집된 최신 원시 누적값을 사용하고, 조회 시각도 남긴다. 화면의 반올림된 값이나 이동 구간의 `rate`·`increase` 추정값으로 정확한 건수를 대조하지 않는다.

현재 `TelemetryMetrics`는 시작 시 success·failure 카운터를 모두 등록한다. 시계열이 보이지 않으면 0으로 간주하지 말고 수집 상태를 확인한다. 대조 중 Backend 재시작이나 카운터 초기화가 발생하면 해당 실행의 카운터 차이는 판정에 사용하지 않는다.

### 4. 실행별 기록표

새 실험 문서에 아래 표를 복사해 실행별로 채운다. 아직 실행하지 않은 값은 `미측정`으로 남긴다.

| 시점 | 조회 시각 | 전체 행 수 | 대상 차량 행 수 | 저장 성공 누적 | 저장 실패 누적 |
|---|---|---:|---:|---:|---:|
| 예열 전 | 미측정 | 미측정 | 미측정 | — | — |
| 본 측정 직전 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 |
| 본 측정 종료 후 | 미측정 | 미측정 | 미측정 | 미측정 | 미측정 |
| 종료 후 − 본 측정 직전 | — | 미측정 | 미측정 | 미측정 | 미측정 |

DB와 카운터의 조회 시각이 다르면 각각 기록한다. 두 조회 사이에 다른 쓰기 작업이 없어야 한다.

정상 대조 기준은 다음과 같다.

```text
k6의 telemetry accepted 성공 체크 건수
  = 저장 성공 카운터 증가량
  = 전체 행 증가량
  = 대상 차량 행 증가량

저장 실패 카운터 증가량 = 0
```

한 값이라도 다르면 실제 차이를 남기고 바로 저장 누락으로 단정하지 않는다. 예열 포함 여부, 다른 쓰기·삭제, 수집 지연, 처리 중 요청, 카운터 초기화, 조회 트랜잭션 상태를 먼저 확인한다. 건수가 일치했다는 결과는 저장 건수 대조이며 개별 데이터 내용까지 검증했다는 의미는 아니다.
